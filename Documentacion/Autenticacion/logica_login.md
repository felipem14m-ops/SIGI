# Login

La lógica de esta funcionalidad se maneja principalmente desde la vista auth/login.php.

Para realizar esta acción, el usuario interactúa con el formulario de inicio de sesión que muestra dos campos: email y contraseña. El javascript de la página puede agregar validaciones básicas del lado del cliente como verificar que los campos no estén vacíos y que el email tenga formato válido, pero las validaciones de seguridad reales se hacen en el servidor.

Al momento de enviar los datos, el formulario en su atributo action está conectado directamente con el archivo AuthController.php con el parámetro accion=login. Dentro de este controlador, el sistema pasa por la acción o función llamada login en función principal.

Cabe recordar que este controlador incluye todos los archivos de configuración como database.php para tener permisos en la base de datos, y se apoya en el modelo Usuario.php necesario para interactuar con la tabla usuarios. Una vez que el controlador recibe los datos del formulario, captura el email y la contraseña, aplica trim para eliminar espacios en blanco, y valida que ninguno esté vacío. Si alguno está vacío, muestra un mensaje de error y redirige de vuelta al login. Si ambos campos tienen contenido, el controlador llama al método buscarPorEmail del modelo pasándole el email ingresado.

El modelo Usuario.php ejecuta una consulta SQL de tipo SELECT con JOIN para buscar el usuario por su email y traer también el nombre de su rol. La consulta trae todos los campos del usuario incluyendo la contraseña hasheada, el estado activo, los intentos fallidos y la fecha de bloqueo si existe. Si no encuentra ningún usuario con ese email, retorna false. Si encuentra el usuario, retorna un array con todos sus datos.

El controlador recibe la respuesta del modelo. Si es false, significa que el email no existe en el sistema, entonces incrementa un contador de intentos en sesión y muestra un mensaje genérico de credenciales inválidas sin especificar si fue el email o la contraseña lo que está mal, esto es una medida de seguridad para no dar pistas a posibles atacantes. Si el modelo retornó datos del usuario, el controlador primero verifica el campo activo. Si activo es 0, muestra un mensaje indicando que la cuenta está desactivada y que debe contactar al administrador, y no continúa con el proceso de login. Si activo es 1, el controlador verifica el campo bloqueado_hasta. Si existe una fecha de bloqueo y esa fecha es mayor a la fecha actual, significa que el usuario está temporalmente bloqueado por múltiples intentos fallidos, entonces muestra un mensaje indicando hasta cuándo está bloqueado y no continúa con el proceso. Si no está bloqueado o el bloqueo ya expiró, el controlador procede a verificar la contraseña usando password_verify comparando la contraseña ingresada con la contraseña hasheada almacenada en la base de datos.

Si password_verify retorna false, significa que la contraseña es incorrecta. El controlador incrementa el campo intentos_fallidos del usuario en la base de datos. Si los intentos fallidos alcanzan un límite configurado como 5 intentos, el controlador establece el campo bloqueado_hasta con una fecha futura como 30 minutos desde ahora, bloqueando temporalmente la cuenta para prevenir ataques de fuerza bruta. Luego muestra un mensaje genérico de credenciales inválidas y redirige al login. Si password_verify retorna true, significa que la contraseña es correcta y el usuario puede acceder. El controlador resetea los campos intentos_fallidos a 0 y bloqueado_hasta a NULL en la base de datos para limpiar cualquier intento fallido anterior. Luego crea la sesión del usuario estableciendo variables de sesión como logged_in en true, y un array usuario con todos los datos relevantes: id_usuario, nombre, email, rol. También puede establecer la fecha y hora del último login. Finalmente redirige al usuario a su dashboard correspondiente: si el rol es Administrador redirige a Admin.php, si el rol es Empleado redirige a Empleado.php.

Al finalizar el proceso, el usuario está autenticado en el sistema y puede acceder a las funcionalidades según su rol. La sesión se mantiene activa mientras el usuario navega por el sistema. Si el usuario cierra el navegador o la sesión expira por inactividad, deberá volver a hacer login. Todas las páginas del sistema validan la sesión al inicio para asegurar que solo usuarios autenticados puedan acceder.
